# Chamithu: stations, energy windows and maps

This component adds MongoDB station inventory, Backoffice/Grid Operator web screens, and native Android geographic discovery. The API owns validation, schedules, inventory calculations and deactivation rules. Clients use REST only. Android's existing SQLite account cache is unchanged; station availability is always fetched online.

## Run and check in Visual Studio

1. Open `SolarMicrogrid.sln` in Visual Studio 2026. Install the ASP.NET/web workload and a .NET 10 SDK matching `global.json` (10.0.300 or a later .NET 10 feature band).
2. Stop any earlier API/web debugging sessions before rebuilding. Otherwise Windows may lock the Debug DLLs.
3. For local MongoDB, start Docker Desktop and run `docker compose up -d mongo` from the repository root. If the API's local settings already point to Atlas, use that connection instead. Atlas configuration belongs in the API, not Web.
4. Run `py scripts/init_dev.py` once. This preserves existing local settings. The staff credentials are in `.local/development-credentials.txt` when generated by the script.
5. Configure multiple startup projects: `SolarMicrogrid.Api` = Start, `SolarMicrogrid.Web` = Start, Contracts = None. Select their `http` profiles and press F5.
6. Open `http://localhost:5080/health` and confirm `{"status":"healthy"}`. Open `http://localhost:5081` and sign in as Backoffice.
7. Open **Microgrid stations → Register station**. Example test values:

   | Field | Value |
   |---|---|
   | Name | Colombo Solar Hub |
   | Address | 10 Solar Road, Colombo |
   | Latitude / longitude | 6.9271 / 79.8612 |
   | Power capacity | 50 kW |
   | Battery storage | 100 kWh |
   | Battery slots | 4 |

8. On the station detail page, keep a schedule that includes the date you will test (default: every day, 08:00–18:00). Add a window two days from today, 09:00–10:00 Sri Lanka time, with 4 usable slots and 40 usable kWh.
9. Edit the station's details, change its schedule, and update a window's usable availability. The UI displays validation/conflict messages returned by the API. A second tab with stale data must reload after a conflict.
10. Create a Grid Operator account through **Team & access**, then sign in as that user. Station list/details, schedule and window availability controls are available; station registration, physical details and activation/deactivation are Backoffice-only.

An inactive station disappears from prosumer discovery. It remains visible to staff. Overlapping windows, invalid GPS coordinates, windows outside operating hours, and inventory above physical capacity are rejected.

## Run and check in Android Studio

1. Open `mobile/SolarMicrogrid.Android` as the project and use JDK 17 with Gradle.
2. Install SDK Platform 36. Use a physical Android device with Google Play services, or a Google Play emulator.
3. Enable **Maps SDK for Android** in Google Cloud and configure billing. Restrict the key to the Android application ID and signing certificate SHA-1 fingerprint. Debug builds use `lk.solar.microgrid.debug`; release builds use `lk.solar.microgrid`.
4. Create or update `mobile/SolarMicrogrid.Android/development.properties` (ignored by Git):

   ```properties
   apiBaseUrl=http://10.0.2.2:5080/api/v1/
   mapsApiKey=YOUR_GOOGLE_MAPS_API_KEY
   ```

   For a USB phone, set `apiBaseUrl=http://127.0.0.1:5080/api/v1/` and run `adb reverse tcp:5080 tcp:5080`. The sample `development.properties.example` documents both settings.
5. Sync Gradle and Run `app`. Keep the API running. Sign in as a prosumer and select the **Explore** tab (or **Explore stations** on Home).
6. The Google map plots active stations from REST. Pan or pinch to explore; tap a marker or station card for current details, schedules and availability.
7. Tap **Use my location** and grant foreground location access to filter within 25 km. The map and station list remain usable if location access is declined.
8. Test pagination, empty nearby results, and station deactivation. The phone needs internet for Google map tiles and a separate connection to the central API for station data.

The API key is inserted into the APK manifest at build time, so an ignored local file alone does not secure it. Use Google Cloud Android app and API restrictions. Release builds require `-PmapsApiKey=...` and an HTTPS `-PapiBaseUrl=...`.

## Station and slot API contract

Base path: `/api/v1/stations`. All endpoints require the existing bearer token. Responses use camelCase JSON and standard Problem Details on errors. Station IDs and slot IDs are generated UUID strings and never change on edits. Database collection: `solarStations`.

| Method/path (relative to base) | Permission | Input/purpose |
|---|---|---|
| `GET /` | Any signed-in account | Staff list all; prosumers see active only. `activeOnly`, `page` (default 1), `pageSize` (1–100, default 20) |
| `GET /?latitude=6.9271&longitude=79.8612&radiusKm=25` | Any signed-in account | Both coordinates required together. Radius 0.1–500 km. Nearest first; `distanceKm` is server-calculated |
| `GET /{id}` | Any signed-in account | Full details; inactive stations are hidden from prosumers |
| `POST /` | Backoffice | Create station |
| `PATCH /{id}` | Backoffice | Replace editable physical fields, plus `version` |
| `POST /{id}/status` | Backoffice | `{ "version": 1, "active": false }` |
| `PUT /{id}/schedule` | Staff | `{ "version": 1, "days": [1,2,3,4,5], "opensAt": "08:00", "closesAt": "18:00" }` |
| `POST /{id}/slots` | Staff | Create a non-overlapping dated energy window |
| `PUT /{id}/slots/{slotId}/availability` | Staff | `{ "version": 2, "usableSlots": 4, "usableEnergyKwh": 40 }` |
| `POST /{id}/slots/{slotId}/archive` | Staff | `{ "version": 3 }`; remove an unused window or archive ended history with no active reservations |
| `POST /{id}/slots/{slotId}/allocations` | Staff / trusted booking workflow | Reserve capacity using a stable booking-allocation ID |
| `POST /{id}/slots/{slotId}/allocations/{bookingId}/cancel` | Staff / trusted booking workflow | `{ "version": 4 }`; release inventory with ≥12 hours' notice |
| `POST /{id}/slots/{slotId}/allocations/{bookingId}/complete` | Staff / trusted transfer workflow | `{ "version": 4 }`; complete after the window starts |

Create payload:

```json
{
  "name": "Colombo Solar Hub", "address": "10 Solar Road, Colombo",
  "latitude": 6.9271, "longitude": 79.8612,
  "capacityKw": 50, "storageKwh": 100, "batterySlots": 4
}
```

Slot payload (replace dates with future dates):

```json
{
  "version": 1,
  "startsAt": "2026-10-01T09:00:00+05:30",
  "endsAt": "2026-10-01T10:00:00+05:30",
  "usableSlots": 4, "usableEnergyKwh": 40
}
```

Allocation payload:

```json
{ "version": 2, "bookingId": "booking-123-attempt-1", "slots": 1, "energyKwh": 10 }
```

Every successful mutation returns the full updated station and its new `version`. Send that version in the next mutation. A stale version returns **409**; reload and explicitly retry. Repeating an identical committed allocation/cancel/complete request returns its result without deducting/releasing again, even if the original version is stale. Reusing an allocation ID with different quantities/status/window is rejected.

Station response fields: `id`, `name`, `address`, `latitude`, `longitude`, `capacityKw`, `storageKwh`, `batterySlots`, `active`, `version`, `schedule`, `activeReservations`, `slots`, `distanceKm` (null without geographic search). List responses are wrapped in `{items,total,page,pageSize}` and include only the next future window per station; detail responses contain all windows for staff and future windows for prosumers.

Slot response fields: `id`, `startsAt`, `endsAt`, `usableSlots`, `usableEnergyKwh`, `availableSlots`, `availableEnergyKwh`, `activeReservations`, `allocations`. Staff detail responses include allocation IDs/quantities/status; prosumers and list responses receive no allocation records. Mobile should fetch details by the marker's station ID before presenting booking information.

## Inventory rules and integration with Sajith / Pasindu

- Schedules are weekly, in **Asia/Colombo (UTC+05:30)**. Day numbers are Sunday=0 through Saturday=6. At least one distinct day is required. Overnight hours/windows are not supported.
- Physical power is measured in **kW**; storage and per-window energy are **kWh**. A window's usable energy cannot exceed either station storage or `power × duration`. Windows at one station cannot overlap; battery slots are shared across those windows.
- Usable inventory is the operator-defined total for a window, including reserved/completed use. The API derives available inventory; clients must not subtract a second time. Cancellation returns inventory. Completion ends the active reservation but retains consumed inventory in that window.
- Station deactivation and reservation allocation update the **same MongoDB document using compare-and-swap on its version**. Exactly one competing write succeeds. This works with standalone MongoDB as well as Atlas and prevents a check-then-write race across collections.
- New allocations must start in the next seven days. Cancellation needs at least twelve hours' notice. Reserved records do not silently expire when the window ends: the booking/operator workflow must cancel or complete them. Thus an unresolved active reservation continues to block deactivation.
- **Sajith:** use `StationService.ReserveAsync` from the booking service inside the central API, or the protected staff allocation endpoint from an authorized operational workflow. Keep `stationId`, `slotId` and the immutable allocation ID in the booking record. Validate booking ownership, approval/payment and booking status in your booking service before calling station inventory. Prosumers cannot call the inventory mutation endpoints directly.
- For a reservation change, the booking workflow must enforce its update policy and coordinate release/acquisition; this component does not provide a cross-station atomic booking-move operation. Do not independently write counters in a bookings collection. If booking persistence is separate, use a durable pending workflow/outbox and reconcile retries with the same allocation ID. Do not expose a booking as confirmed until its allocation is committed. Ordinary cancellation is not a substitute for a compensation protocol inside the 12-hour cutoff.
- **Pasindu:** resolve the server booking after validating the QR code, then call `EndAllocationAsync(..., complete: true)` / the complete endpoint. QR verification, ownership checks and transfer measurement remain in your component. Retrying completion is idempotent. Stable station/slot IDs can be referenced by QR workflows; a QR payload alone is not authorization.
- No booking or QR implementation was present when this component was added. The allocation ledger and contracts are ready for integration; they do not validate the existence of an external booking record. Active usage shown on the web comes from that ledger. No message has been sent to other team members.
- Up to 500 windows per station and 100 allocation records per window keep a station document bounded. Archive ended windows only after booking history has been retained by the booking component. Archiving removes the station's copy of that window/allocation history. Repeated allocation IDs are remembered only while their window remains; booking records must retain long-term deduplication/history. Geographic discovery currently computes distance on the API from stored coordinates; larger deployments should move this to a MongoDB geospatial index/query.

## Verify active-reservation deactivation protection manually

Use Visual Studio's HTTP client with `docs/stations.http` or another REST client:

1. Log in as staff and use the returned bearer token.
2. Create a station and a window at least 12 hours in the future and within seven days.
3. Reserve one slot through the allocation endpoint. The web detail page now shows its allocation ID and reduced availability.
4. Try **Deactivate station** as Backoffice: expect a clear error and API **409**.
5. Try reducing usable inventory below the reservation: expect **409**.
6. Cancel the allocation through the API using the latest version: availability returns.
7. Deactivate the station: it succeeds and disappears from the Android map/list after refresh.

## Automated verification

```powershell
dotnet build SolarMicrogrid.sln
py scripts/verify.py --no-build

cd mobile/SolarMicrogrid.Android
.\gradlew.bat assembleDebug testDebugUnitTest lintDebug
```

The Python runner uses a fresh temporary MongoDB database and separate ports; it does not modify development accounts/stations. Put `mongod` on PATH, or set `TEST_MONGO_URL` to a disposable server. Typical Windows installation:

```powershell
$env:PATH = 'C:\Program Files\MongoDB\Server\8.0\bin;' + $env:PATH
```

If Debug is running in Visual Studio, verify separately with `dotnet build SolarMicrogrid.sln -c Release` followed by `py scripts/verify.py --no-build --configuration Release`. For just the station tests add `--test test_00_stations.StationTests`. Generated OpenAPI is refreshed at `docs/openapi.json`; Development serves the live schema at `/openapi/v1.json`.
